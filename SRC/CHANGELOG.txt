Changelog:

Version 1.2 - 2026-11-04

Register context guard (new, generic)
- WINSIMD.SYS (x86) and WINSIMD.VXD now preserve the SIMD register files the
  operating system does not save across thread switches. XMMGUARD/LOADXMM
  are no longer needed.
- Mechanism: a hook on vector 7 (#NM, device not available) in front of the
  OS handler. Every supported scheduler switches the FPU lazily (CR0.TS), so
  the first x87/MMX/SSE/AVX/AVX-512 instruction of a thread that does not own
  the registers traps there. The guard then stores the registers of their
  previous owner and loads those of the new thread. Ownership follows the OS's
  own FPU ownership. The mechanism is not tied to any kernel build or
  offset.
- Saved components are exactly those the OS does not manage:
  XMM0-7 + MXCSR (NT 3.1/3.5x/4.0, Windows 95, Windows 98 first edition);
  YMM upper halves, opmask and ZMM (every target), using XSAVE/XRSTOR with
  that component mask. Without XSAVE, MOVUPS/STMXCSR are used.
- Multiprocessor NT: when a thread resumes on a different CPU while its values
  are still in another CPU's registers, the new CPU sends an NMI through the
  local APIC. The other CPU's NMI hook stores the values and releases them.
  Nobody waits while holding the table lock, and a waiting CPU serves requests
  addressed to itself, so CPUs cannot block each other. A real NMI still goes
  to the OS handler (task gate or interrupt gate).
- Thread state slots: 1024 (XMM) or 384 (XSAVE) per system, taken from
  non-paged pool or the VMM heap. They are released on thread exit
  (PsSetCreateThreadNotifyRoutine on NT 4.0+, Destroy_Thread on 9x). Without
  a notification (NT 3.1/3.5x), the least recently used slot that is not
  loaded in a CPU is reused.
- Status: NT publishes a CG_STATUS block in the VOLATILE key
  HKLM\SYSTEM\CurrentControlSet\Services\winsimd\Runtime (values Guard,
  GuardFlags, GuardComponents, GuardReason, Version). The key disappears at
  shutdown, so a stale value can never claim protection. 9x:
  DeviceIoControl(\\.\WINSIMD, 2) returns the same block. WINSINFO shows the
  preserved register files. The guard can be turned off with
  ContextGuard=0 (REG_DWORD) in the service key.
- amd64 (XP x64 / Server 2003 x64): the kernel saves XMM/MXCSR itself (eager
  fxsave/fxrstor in SwapContext) but not the YMM upper halves. Because the FPU
  is switched eagerly there is no #NM trap, so the amd64 guard preserves
  YMM0-7 upper halves by hooking SwapContext directly (src/guardx64.c):
  * the kernel base is found from WINSIMD's own DbgPrint import and the
    SwapContext site from a unique byte signature, used only if it occurs
    exactly once - no fixed address, RVA, build stamp or KPRCB offset; per-CPU
    identity is the KPRCB pointer, registered on first sight;
  * the 14-byte absolute-jmp hook is installed under KeIpiGenericCall;
  * slots are freed on thread exit (PsSetCreateThreadNotifyRoutine); the hot
    path makes no kernel calls;
  * it guards YMM only, not AVX-512 ZMM/opmask.
  PatchGuard: XP x64 / 2003 SP1 hash-check the kernel's code and bugcheck
  (0x109) on any SwapContext patch. To be safe the hook is installed ONLY when
  PatchGuard is genuinely disabled - a kernel debugger attached
  (KdDebuggerEnabled=1 and KdDebuggerNotPresent=0). On a normal boot the guard
  detects PatchGuard is active, touches nothing, and reports GuardReason
  CG_PATCHGUARD, so WINSIMD never bugchecks the machine. SSE/XMM apps (the
  Flash Player ports included) need no guard on XP x64. AvxPolicy still applies.

Installer (WINSIMD.EXE)
- GUI by default: a Yes/No confirmation, a self-drawn progress bar (works on
  NT 3.1, which has no comctl32), and a "completed" message box.
- /silent installs with no UI and prints "completed." to the console.
- /remove uninstalls WINSIMD if present (GUI, or /silent for console only).
- Console start-type/policy/control flags (/auto /system /boot /demand /safe
  /avx start stop) are unchanged.

Fixes
- Installer: the stale "'ilfinst start' to load now" hint is gone; it now
  prints "Restart Windows to load the driver.".
- CR4 is per processor: ilf_apply_policy now starts from the running CPU's
  CR4. Before, every CPU after the first received the boot CPU's updated copy,
  the write looked unnecessary, and SSE stayed off on application processors
  (#UD on the second CPU).
- NT 3.1/3.5x multiprocessor: these kernels export no KeSetSystemAffinityThread,
  so 1.1 programmed only the boot CPU. CPUs are now reached with
  NtSetInformationThread(ThreadAffinityMask), and the driver waits until the
  thread really runs on the target CPU (KPRCB SetMember).
- Thread slots are zero-filled at start: XRSTOR raises #GP when the reserved
  bytes of an XSAVE header are not zero, and XSAVE does not write them (seen
  as STOP 0x7F/0xD on Windows 2000 with AVX before the fix).
- The guard clears CR0.EM as well as CR0.TS around its own register accesses
  (the NT 3.1 MP kernel keeps EM set while no thread owns the FPU).

Verified in QEMU (60-second stress tests; counts are failed register checks)
- NT 3.1 UP, XMMSTRS (3 threads):        1.1: about 680 per thread, 1.2: 0
- NT 3.1 UP, AVX CPU, YMMSTRS (3 threads): 1.1: about 680 per thread, 1.2: 0
- Windows 95 RTM, XMMSTRS (3 threads):    1.1: about 700 per thread, 1.2: 0
- NT 3.1 MP (2 CPUs, NTCPUPAE kernel), XMMSTR6 (6 threads): 1.2: 16679 and
  21064 checks in two runs, 0 failures. In the instrumented run, cross-CPU
  transfers occurred and every one was served by the flush NMI. With 1.1
  the test cannot run there (SSE is off on CPU 1).
- Flash Player 32 + Super Mario 63 ran for 4 minutes of random input on
  NT 3.1 with 2 CPUs and WINSIMD 1.2, without a fault.
- NT 4.0 UP, XMMSTR6 (6 threads): 9901 checks, 0 failures.
- Windows 2000 UP, AVX CPU, YMMSTRS (3 threads): 0 failures.
- Windows 2000 MP (2 CPUs), AVX CPU, YMMSTRS (3 threads): about 5000 checks
  per thread, 0 failures. WINSINFO shows "Registers preserved by WINSIMD: YMM".
- Windows 95 RTM with the final VxD: XMMSTRS 3382/2592/2911 checks,
  0 failures; WINSINFO shows "Registers preserved by WINSIMD: XMM".
- Flash Player 32 starts and plays on NT 3.1 UP, NT 4.0 and Windows 95 with
  WINSIMD 1.2 alone. Flash Player 10 reports SSE2 mode on Windows 95.
- XP x64 amd64 YMM guard: with PatchGuard disabled (kernel debugger attached)
  the SwapContext hook arms (GuardFlags = ACTIVE|YMM), the hook runs on every
  thread switch, and the system reaches the desktop and runs stably; the
  signature scan found SwapContext uniquely (rva 0x54c48 on 5.2.3790.1830).
  Without that - a normal boot - the guard correctly reports CG_PATCHGUARD and
  does not patch, and the machine is stable. (A full PatchGuard-off YMMSTRS
  pass is prevented by PatchGuard itself, not by the guard.)
- XP x64: both Flash Player 10 and Flash Player 32 run (OS-managed XMM; no
  guard needed).
- Installer verified on XP x64: GUI confirmation dialog, self-drawn progress
  bar and "completed" message box; /silent installs with no UI and prints
  "completed."; /remove deletes the service and driver file and reports it.
Not verified: NT 3.5x (the available image does not boot in this QEMU),
Windows 98 first edition, AVX-512 hardware, real (non-emulated)
multiprocessor machines, more than two CPUs with 1.2, and a full YMM stress
pass on XP x64 with PatchGuard disabled on real hardware.

Known issue (test environment)
- With an artificial QEMU CPU model (pentium3 + xsave + avx, level=13) the
  CR4.OSXSAVE write never returns, in 1.1 as in 1.2, and NT 3.1 hangs. With
  QEMU "-cpu max" and real AVX CPUs this does not occur.

Version 1.2 - development checkpoint, 2026-11-01 (superseded by 1.2 above)

- Added exact-kernel NT 3.1 UP/MP XMM0-XMM7 and MXCSR preservation research code.
- Added four-worker preemption and verified native-NT affinity migration tests.
- Verified a four-CPU run with 342 affinity rounds and zero XMM/MXCSR/x87 errors.
- Fixed NT 3.1 CPU-coverage diagnostics to use the KPRCB affinity mask; all four
  CPUs are now observed (mask 0xF).
- Passed 640 worker lifetimes with zero errors; observed 647 retired slots
  including test/control threads, with a peak of 41 active slots.
- Verified the current driver and loader after a clean UP reboot: four workers,
  zero XMM/MXCSR/x87 mismatches.
- Refused replacement of an already-running research driver in LOADXMM.
- Retained the bounded 512-entry table and exact-kernel checks; production
  installation rendezvous and broader OS integration remain unfinished.
- YMM and ZMM context preservation is not implemented. This is not an AVX or
  AVX-512 concurrency fix, and it is not a universal WINSIMD 1.2 release.
